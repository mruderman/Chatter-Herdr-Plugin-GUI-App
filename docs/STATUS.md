## Found 2026-10-11 and 12, for Flan (proposed number F16; nothing applied yet)
- **F16, bridge:** `PATCH /v1/members/{h}` (`updateMember`, `bridge/src/store.js:99`) validates nothing that `addMember` validates. T7's executor ran it against a real bridge on 2026-10-11 and its integration test asserts what follows (I read the test; I have not run these calls myself). A bad `kind` or `role` answers 500 `internal` (POST: 400 `bad_kind`, `bad_role`). A login another member holds answers 500 `internal` "internal error" (POST: 409 `login_taken`). A revoked member keeps its login, so adding someone with it answers 500 `internal` too (the bridge's check looks at active members only); clearing the login by PATCH on the revoked row frees it, which is why Edit stays on revoked rows. PATCH `{}` answers 200 and writes a `member_update` audit entry; a display name of `""` is stored, and a login of `""` is stored as `""` (a second member doing that gets the 500). Nothing is written when it fails and no policy is crossed, so the cost is a vaguer message in the admin panel and, for the empty cases, noise in the audit log. Recommended default: a small bridge task (same files as T11) that mirrors `addMember`'s checks in `updateMember` and refuses an empty patch, with a regression test per case; or defer to M4 if you would rather keep M3's diff to the client.
- Same source: revoking an already revoked member answers 200 and writes another audit entry; rotating a revoked member answers 404 `no_such_member`; demoting or revoking the last admin answers 409 `last_admin` (the panel shows it in the dialog); revoking or rotating yourself answers 200 and 201, your own streams get `bye` `revoked` or `token_rotated`, and the old token then gets 401 `bad_token`. The panel works around these (a revoked row offers only Edit; an unchanged Edit form is refused before it is sent).
- **Own-token rotation in a token session (read, not run in the integrated app):** an admin who rotates their own token while signed in with a token gets `bye token_rotated` on their own stream; the client retries after a jittered 0 to 1 s (`client/src/api/stream.ts` line 217 and `DEFAULT_STREAM_TIMING`), the old token is refused with 401, and the store ends the session. The page returns to Sign in and the dialog that holds the new token goes with it. Signed in through the tailnet identity (production) the reconnect succeeds and nothing ends. The confirmation says "your current token stops working at once" but not that this session ends. No spec covers it. Recommended default: leave it for M3 (it needs a token session and an admin rotating their own account, and `chatter-bridge token` on the host issues another); if you want it handled, the smallest change is a sentence in the confirmation, and a real fix (keeping the dialog alive across sign-out) is a bigger change.
